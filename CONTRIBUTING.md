# Contributing to Embyr

Embyr is developed through small, reviewed increments. Keep every change tied to
an explicit problem and within the accepted product and architecture boundaries.

## Main Branch

`main` is the protected, stable branch.

- Do not develop directly on `main`.
- Do not force-push `main`.
- Do not rewrite published history.
- Merge changes into `main` through pull requests.

## Branch Names

Use short-lived branches with one of these prefixes:

- `feat/` for product capabilities
- `fix/` for defect corrections
- `refactor/` for behavior-preserving restructuring
- `test/` for test-only work
- `docs/` for documentation
- `chore/` for repository maintenance
- `research/` for experiments and investigations

Use a short, descriptive kebab-case name after the prefix.

## Issues

Non-trivial work starts from a GitHub Issue that defines:

- Problem
- Goal
- Scope
- Acceptance Criteria
- Dependencies
- Out of Scope

Do not begin implementation until the issue is specific enough to verify.

## Pull Requests

Every implementation pull request explains:

- what changed;
- why it changed;
- how it was tested or otherwise verified;
- the related issue;
- any database or migration impact; and
- known limitations.

Keep the change limited to the issue. Update the branch instead of bypassing a
failed check or unresolved review feedback.

## Commits

Use small, coherent Conventional Commit-style commits. Accepted prefixes include
`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `perf:`, `chore:`, `ci:`,
`build:`, and `research:`.

## Definition of Done

An issue is complete only when:

- the implementation exists;
- tests pass;
- required verification passes;
- documentation is current;
- the pull request is reviewed;
- the pull request is merged; and
- every acceptance criterion is satisfied.

## Database Migrations

Once a SQL migration reaches `main`, it is immutable. Correct mistakes with a
subsequent migration; never edit the merged migration.

## API Contracts

Client functionality must not rely on undocumented backend behavior. Add or
update the reviewed API contract in the same pull request as a contract change.

## Frozen Decisions

Do not silently redesign a frozen product or architecture specification during
implementation. A proposed change requires evidence from at least one of:

- implementation constraints;
- user testing;
- security findings;
- performance measurements;
- cost measurements; or
- validated product evidence.

Document and review the resulting decision before implementation depends on it.

## Research

Research code belongs under `research/`. Research results do not automatically
become production code; production adoption requires a separately scoped and
reviewed change.

## AI-Generated Code and Agent Scope

Code generated by Codex, ChatGPT, or any other agent receives exactly the same
scope, testing, review, and architecture scrutiny as human-written code.

While implementing an issue, AI agents must not perform unrelated refactors,
dependency upgrades, architecture changes, or product redesigns. Surface useful
out-of-scope findings separately instead of including them in the change.

## Dependencies

Every new dependency requires an explicit technical justification. Explain why
the capability is needed and why the existing stack is insufficient.

## Security and Privacy

Never commit secrets, credentials, tokens, production data, or private user
information. Use synthetic development data unless sanitized real data has been
explicitly approved.

Security-sensitive changes require explicit review. Follow
[`SECURITY.md`](SECURITY.md) when reporting vulnerabilities.

## Documentation

Architecture, schema, API, and workflow changes update their documentation in
the same pull request.

## Work in Progress

Prefer one major task and, at most, one small secondary task at a time. Do not
begin every subsystem simultaneously.

Prefer working end-to-end vertical slices over completing every backend
subsystem before integration. A slice should provide a verifiable capability
across only the layers it actually needs.
