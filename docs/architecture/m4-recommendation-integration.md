# M4 Recommendation Integration

This is the implemented backend path for [`production-recommendation/v1`](../api/production-recommendation-service-contract-v0.1.md), using the frozen [`m3-simulation/v5` contract](../../research/recommendation/simulation-contract-v0.1.md) decision mechanics and the [v0.1 API](../api/api-contracts-v0.1.md). The first release produces one learning-entity recommendation. `CREATE` returns the replayable empty result until practical targets are added. The [M3 findings](../../research/recommendation/FINDINGS.md) record limitations carried into production.

## Request path

1. `POST /api/v1/recommendations/next` authenticates a Supabase token and resolves its internal `app_users.id`. The route checks an unexpired idempotency result before work begins.
2. `snapshot.py` opens one RLS-scoped PostgreSQL `REPEATABLE READ READ ONLY` transaction as `app_backend`, with transaction-local `app.user_id`. It captures all logical input reads: reviewed/published ontology versions, edges, current document embeddings, explicit preferences, exploration history, and learner projections. ACTIVE exploration targets and current-version MORE targets form the sorted, deduplicated anchor set. The transaction closes before any provider call.
3. Whenever that detached snapshot has both anchors and valid document embeddings, `service.py` makes one deterministic `semantic-query-text/v1` query per sorted anchor, regardless of request mode. Its exact text is `TITLE: {canonical_title}\nSUMMARY: {canonical_summary}` with one newline, no other anchors, and no learner-authored query. `VoyageQueryEmbedder` sends it to `voyage-ai`/`voyage-4` as `input_type=query`, yielding 1024-D vectors. Provider code is outside the ranking domain.
4. `retrieval.py` nominates the full five-source population independently of mode: GRAPH, SEMANTIC, EXPLICIT_INTEREST, HISTORY_CONTINUATION, and REVISIT. It uses M3 source normalization and hard eligibility. `recommendation-retrieval/v1` applies per-anchor exact cosine search with a 0.55 floor, merges targets before the global 40-candidate cap, uses each target's strongest similarity for its feature, and retains qualifying source paths. RELATED_TO is bidirectional, bounded to two hops and 100 distinct targets, with deterministic shortest-hop ordering. No ANN index is used.
5. `ranking.py` scores the eligible population with frozen M3 features, applies deterministic pre-rerank ordering, `DOMAIN_COVERAGE`, and explanation codes, then applies a stable mode filter before production `top_k = 1`. CONTINUE requires HISTORY_CONTINUATION; REVISIT requires REVISIT; EXPLORE requires GRAPH, SEMANTIC, or EXPLICIT_INTEREST; SURPRISE requires GRAPH or SEMANTIC and no EXPLICIT_INTEREST; CREATE has no learning-entity survivor in v1. Filtering never reranks or removes source paths, preserves each survivor's original `final_rank`, permits an empty result, and has no cross-mode fallback. `ProductionRanking.ranked` remains the full pre-filter ranked population; `selected` is the first post-filter survivor or null. `distance-band/v1` reads selected transient source paths after selection and never influences M3 score or rank.
6. A separate writable transaction independently sets `app.user_id`, reserves the idempotency generation, and rechecks target deliverability. Its atomic recommendation `INSERT ... SELECT` again requires a REVIEWED/PUBLISHED entity, the exact selected version row, and `current_version` equal to the selected version. It stores compact selected provenance and the durable response, then commits. An empty post-eligibility or post-mode-filter outcome stores replayable HTTP 200 `{"recommendation": null}` without a recommendation row.
7. `POST /api/v1/recommendations/{id}/decision` reserves its command generation, locks the learner-owned recommendation under RLS and an explicit user predicate, and enforces one decision. ACCEPT creates an Exploration retaining `recommendation_id`, derives intent from persisted recommendation mode, and emits ordinal RECOMMENDATION_ACCEPTED then EXPLORATION_STARTED events. SKIP creates no Exploration and emits RECOMMENDATION_SKIPPED. Each command stores its replayable response and commits atomically; no worker participates.

The write transaction can observe later ontology state than the input snapshot. If the route recheck or later atomic INSERT guard finds the selected target no longer deliverable, the transaction rolls back its reservation and recommendation writes and responds HTTP 503 `RECOMMENDATION_GENERATION_UNAVAILABLE`. It neither upgrades to a new version, presents a historical superseded version, nor regenerates within the command. A future request may use a fresh snapshot. Concurrent same-key calls can repeat generation work, but the active command reservation serializes the write and yields one persisted result.

## Version and data mapping

| Production source | M3 meaning | Production policy |
|---|---|---|
| `learning_entities`, versions, domains, objectives | Ontology target and scoring context | Historical versions remain readable; only the current version of a REVIEWED/PUBLISHED entity can be delivered. |
| `ontology_edges` | RELATED_TO and objective-relative REQUIRES | A REQUIRES edge runs from dependent candidate to prerequisite, with exact source/target versions and an objective belonging to the target version; malformed active edges fail closed. |
| `learner_objective_state.categorical_state` | Objective readiness | `UNDERSTOOD`/`RETAINED` satisfy; absent state is UNKNOWN. Numeric estimates are not used as a threshold. |
| `learner_interest_state`, `learner_challenge_state` | Inferred affinity and area ability | Recent and long-term interest stay distinct; missing ability remains missing. |
| Explicit preferences and `explorations` | Explicit nomination, continuation, revisit, anchors | PAUSED and NOT_INTERESTED hard-exclude. ACTIVE supports continuation; COMPLETED supports revisit. |
| `entity_embeddings` | Semantic document space | Only current `voyage-ai`/`voyage-4`/1024/`ontology-entity/v1` rows with `input_type=document` and a matching canonical-text fingerprint enter exact cosine search. |
| Checked-in JSON profiles | Ranking, retrieval, distance, presentation | `recommendation-profile/v1`, `recommendation-retrieval/v1`, `distance-band/v1`, and `recommendation-copy/v1` are immutable identities. |

The final M4 migration chain is `0014_objective_categorical_state` → `0015_retrieval_expand` → `0015_recommendation_retrieval` → `0016_recommendation_reason` → `0017_idempotency_key_reuse`. These respectively add categorical learner objective state; stage nullable version/objective fields for legacy REQUIRES curation; enforce versioned REQUIRES, Voyage document identity, and `vector(1024)` after curation and clearing old derived vectors; allow nullable `reason_code`; and preserve historical command identities across idempotency-key expiry. The retrieval enforcement migration refuses uncurated edges or uncleared old embeddings rather than guessing a prerequisite mapping or re-embedding. Migration 0017 does not change M3 scoring.

For a REQUIRES edge, `UNDERSTOOD` or `RETAINED` on its exact prerequisite objective is SATISFIED; another frozen categorical state is UNSATISFIED; missing evidence is UNKNOWN. A HARD UNSATISFIED requirement excludes as `PREREQUISITE_UNMET`, and HARD UNKNOWN as `INSUFFICIENT_STATE`; SOFT does not hard-exclude. Numeric estimates never become an invented mastery threshold. Challenge ability uses only a matching entity-domain numeric, non-boolean, finite `ability_estimate` in `[0, 1]`: a valid primary domain wins, then the lexicographically first valid matching domain, otherwise no challenge state is passed and M3 gives `difficulty_fit = 0`. Values are not clamped.

The checked-in [`recommendation-profile/v1`](../../backend/app/recommendation/profiles/recommendation-profile-v1.json) fixes eight initial, reviewed weights: readiness 0.14, difficulty_fit 0.18, explicit_interest 0.22, inferred_interest 0.08, graph_proximity 0.12, semantic_similarity 0.14, continuation_value 0.07, and revisit_value 0.05. `DOMAIN_COVERAGE` has diversity_weight 0.08. These values are immutable under the v1 identity and are uncalibrated; they are not a recommendation-quality claim. The separate [`distance-band/v1`](../../backend/app/recommendation/profiles/distance-band-v1.json) policy chooses the closest signal: COMFORT for continuation/revisit/explicit interest; ADJACENT for one graph hop or cosine ≥0.80; FRONTIER for two hops or cosine in `[0.65, 0.80)`; WILD for cosine in `[0.55, 0.65)`. Precedence is COMFORT > ADJACENT > FRONTIER > WILD, default ADJACENT. The band is descriptive and does not change M3 ranking.

The recommendation row stores the exact selected entity/version, request mode, distance band, `recommendation-profile/v1`, selected source categories, all machine explanation codes, original ranked `final_rank`, `shown_position`, compact component scores, pre-rerank score, diversity adjustment, ordering score, `recommendation-copy/v1`, primary canonical `reason_code` or NULL, reviewed hook/reason, and `presented_at`. The first applicable M3 explanation code in canonical order alone selects the static copy template. Zero codes yield NULL `reason_code`, hook, and reason under `0016_recommendation_reason`, without generic fallback or generated prose. Full candidate populations and paths, excluded candidates, raw feature values, configured weights, full scoring/rerank traces, learner snapshots, vectors, and M3 simulation envelopes remain transient.

Experience Ledger events keep bounded factual references such as `recommendation_id`, not duplicate learner state, vectors, traces, excluded candidates, or arbitrary text. `DecisionRequest.reason` is optional and at most 64 characters; it participates in the idempotency fingerprint but is not durably copied into recommendations, Explorations, or `learning_events.metadata`.

## Security and operations

The backend uses `app_backend` with NOBYPASSRLS, FORCE RLS on learner-owned state, and transaction-local `app.user_id`. Canonical ontology is global reference data; recommendation, exploration, and event state is learner-scoped. Recommendation lookup and decision writes additionally predicate on `user_id`. The `app_worker` role and queue are not used for this synchronous path. Both endpoints require `Idempotency-Key`. ACCEPT intent maps CONTINUE to RELATED_EXPLORATION, REVISIT to RETENTION_REVISIT, EXPLORE to DIRECT_INTEREST, and SURPRISE to SERENDIPITY. Future CREATE practical acceptance maps to PRACTICAL_SUPPORT.

Migration `0017_idempotency_key_reuse` permits multiple historical generations of a key after expiry. A partial unique index allows exactly one active `(user_id, idempotency_key)` row where `retired_at IS NULL`. An unexpired active key with the same command and fingerprint replays or remains in progress; a different command or fingerprint returns `409 IDEMPOTENCY_KEY_REUSED`. An expired active generation is retired and a new record with a new UUID is reserved. Its historical UUID and durable result remain, so `learning_events.command_id` references are preserved. The expired row is never overwritten.

Set `EMBYR_VOYAGE_API_KEY` when a request can have both anchors and valid captured document embeddings, regardless of mode. The derived, replaceable corpus uses `ontology-entity/v1` and `input_type=document`. Its exact UTF-8 input is `TITLE: {canonical_title}\nSUMMARY: {canonical_summary}`; `embedding_input_fingerprint` is `sha256:` followed by the 64 lowercase hex digits of that text's SHA-256 digest. The snapshot admits a current document vector only if its stored fingerprint matches the current canonical title and summary. Missing or stale vectors contribute no SEMANTIC path: the service neither relaxes thresholds nor generates or backfills document vectors synchronously. An external/operator ingestion process must refresh the corpus after title, summary, or version changes. M4 provides the versioned read/query adapter, not that writer. Provider, model, or input-version transitions require explicit re-embedding.

Exact search currently loads matching document vectors in the snapshot and compares each anchor to each document in application memory. Cost is O(anchors × documents × 1024); the 0.55 threshold, 40 semantic target cap, two-hop graph bound, and 100 graph target cap are initial uncalibrated policy, not quality or latency claims. No ANN index, provider refresh job, benchmark, load test, recommendation expiry/history endpoint, worker path, Android UI, or practical-target generator is included.

## Verification gate

Focused backend tests cover the input mapper, five retrieval sources, M3 adapter, compact provenance, distance bands, API replay and ownership behavior, and an in-memory snapshot-to-ranking case. [`test_recommendation_flow.py`](../../database/tests/test_recommendation_flow.py) is the targeted disposable PostgreSQL gate for preference → recommendation → ACCEPT → Exploration/events, empty CREATE, ownership, replay, and fingerprint conflict. Run it with a running Docker daemon for Testcontainers or a dedicated disposable `EMBYR_TEST_DATABASE_URL`:

```bash
python -m pytest database/tests/test_recommendation_flow.py -q
```

Across M4 implementation validation, the adjacent disposable database selection passed (68 tests), as did the backend suite (132 tests) and frozen M3 suite (856 tests). Those broad suites were historical stack evidence, not rerun after every later remediation. The final #73 remediation ran 16 focused provenance, API, and disposable PostgreSQL production-role flow/race cases successfully. These checks support deterministic integration, persistence, ownership/RLS, and replay behavior. No live Voyage request, corpus refresh operation, hosted rollout, or scale/load benchmark was exercised; weights and thresholds remain uncalibrated. Passing integration tests does not establish recommendation quality or production-scale latency. No background recommendation worker, Android UI, practical-target generator, or recommendation history/expiry endpoint is included.
